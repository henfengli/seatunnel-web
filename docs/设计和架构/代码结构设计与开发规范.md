## 1. 项目概览

内网单机的 SeaTunnel 作业管理平台：把 kafka / mongodb / postgresql / doris 四种源的数据
同步到 Doris，提供作业创建向导、提交/停止/更新编排、目标表自动建表与演进、数据迁移重建、
监控面板、连接健康测试、批量创建与批量操作、钉钉告警。

**规模假设**：几十条作业、几个用户、单机部署。所有技术选型都按这个规模定，不要按互联网
大厂规模去"升级"它（见 §8 刻意不做的事）。

**技术栈**：FastAPI + Jinja2 SSR + htmx（无前端构建链）+ SQLAlchemy 2.0 / SQLite(WAL)
+ APScheduler 单进程后台看护。模板 38 个、手写 CSS 231 行，静态资源只有 htmx + chart.js。

**体量**：app/ 约 6.5k 行 Python，68 个页面端点；tests/ 约 2.0k 行，39 个 pytest 用例。

## 3. 分层架构与依赖纪律

```
api/pages/* + api/fragments.py   表单校验、跳转、片段渲染（不含业务规则）
        │  ↓ 调用
services/                        全部业务逻辑（编排/DDL/渲染/发现/监控/看护）
        │  ↓ 调用
core/                            config / db / crypto / fmt（无向上依赖）
models.py / templating.py        被各层引用
```

**纪律只有三条**：

1. **依赖方向不可逆**：api → services → core。services 里出现 `Request` 就是错层。
2. **编排一律在 services**：submit/stop/update/delete/migrate 全在 `orchestrator`，路由只做
   表单解析 + `run_in_threadpool` 调用 + `goto`。批量任务编排在 `batch_ops`。
   （历史教训：迁移重建编排曾写在路由里 103 行，第三轮重构才下沉。）
3. **域规则不下放 Web 层**：Doris 模型/TTL 校验在 `field_mapping.apply_model_ttl`，
   类型映射在 `field_mapping.build_mapping`，映射生成在 `mapping_gen.auto_mapping`。
   `pages/common.py` 只放纯表单关注点（取值、正则、错误重渲染），且只收被 2 个以上
   模块复用的东西。

**两个已知的例外（刻意保留，不要"修复"）**：

- `templating.py` import `envs`：base.html 顶栏要环境列表。方向（web 基础设施 → 服务）
  比反过来（services → templating）安全，注释里写了动机。
- 批量向导 `job_batch_create`（batch.py）的路由函数偏重（逐对象校验+建作业+预渲染的
  落库循环）。目前线性可读；**若批量创建后要加编排动作（如直接提交），先把循环下沉
  services，别让它长成第二个 103 行路由。**

## 4. 核心设计

### 4.1 作业状态机与并发防线（全库技术含量最高的部分）

状态：`DRAFT / RUNNING / STOPPED / FAILED / UPDATING / ERROR`（models.JOB_STATUSES，
每个状态有行内注释）。转移全部由 orchestrator 编排函数驱动，watchdog 只做收敛性轮询。

五道防线，各自独立又互相补位：

1. **CAS 原子抢状态**：submit 和 update_and_restart 用
   `UPDATE ... WHERE id=? AND status IN (...)`（synchronize_session=False）抢占，
   批量+手动+双击并发提交出双作业的场景被堵死；CAS 失败 `db.expire` 后重读真实状态再报错。
2. **状态白名单**：`SUBMITTABLE_STATES = (DRAFT/FAILED/ERROR/STOPPED)` 在服务层拦截，
   不依赖调用方自觉。
3. **防双写**：`_find_running_conflict` 查同 env+同数据源+同源对象的 RUNNING 作业，
   从业务根上防"两个作业全量消费同一 topic 写双份"。
4. **远端在跑核实**：`_remote_running`——DB 非 RUNNING 但远端可能实际还在跑
   （上次 stop 失败残留），update 和 migrate 两条编排共用同一标准，核实后按在跑处理。
5. **歧义处理诚实**：update 提交"失败"可能只是响应超时——先查 SeaTunnel 侧实际状态，
   "结果不确定"就明说请人工核对，**不伪造回滚**。

另外两条边界约定：

- **UPDATING 不参与 watchdog 状态轮询**（编排线程自己管），refresh_status 不动 UPDATING——
  避免轮询和编排竞争出假迁移。
- **批量任务不死**：batch_ops 外层兜底保证任务不永远 RUNNING 卡死进度页；进程重启时
  `main._sweep_stuck_batches` 把中断的批量任务标记收敛。

### 4.2 唯一通道 / 唯一入口

这几条"唯一"是三轮重构收敛出来的硬约定，新增代码必须走它们：

| 关注点 | 唯一入口 | 说明 |
|---|---|---|
| SeaTunnel HTTP | `seatunnel_client` | 全库 grep 不到第二个向集群发请求的入口；monitor 的 `_st_get` 也只是薄别名 |
| Doris 连接 | `doris_ddl.connect(doris, read_timeout, autocommit)` | 参数块一处，调用方只传超时/autocommit 差异；兼容环境 dict 与数据源 dict 两种键名 |
| 映射生成 | `mapping_gen.auto_mapping` | 向导预览/批量/表单兜底三处共用；field_mapping 保持纯函数不碰 DB |
| 删除语义 | `orchestrator.delete` | 取消远端 + 删记录 + 清 MetricSample，单个/批量共用 |
| 提交停止更新 | `orchestrator.submit/stop/update_and_restart` | 页面与批量都走这里，没有第二套 |

### 4.3 数据模型与 JsonDict 列

9 张表：Environment / Datasource / ProtoPackage / Job / JobVersion / JobEvent /
MetricSample / BatchTask / BatchItem。

- **JsonDict 列类型**（core/db.py）：TEXT 列存 JSON，Python 侧直接读写 dict/list，
  数据库列名保持 `*_json` 兼容旧库。列声明统一配 `MutableDict/MutableList.as_mutable`：
  **顶层键/元素原地改可落库；嵌套层级的变更仍须整体重新赋值**（docstring 有写明）。
- **conf 加密**：渲染产物含解密后的连接密码，落库一律加密（job.seatunnel_conf 和
  JobVersion.conf），使用方经 `crypto.decrypt_safe` 还原（兼容历史明文行）。
- **options 访问器是模型属性**：`Job.ttl / Job.buckets / Job.table_model`——读作业配置
  不需要 import 编排模块。

### 4.4 配置与环境管理

- **环境存 DB，不存配置文件**：运行时环境一律读 DB（Web 上增删改）。
  `environments.yaml` 的 environments 段只是**首次启动的种子**，由 `.env_seeded`
  标记文件保证只导入一次（不是"表为空才导入"——删光环境不会复活种子）。
- **改 YAML 必须重启进程**（README 有说明）；watchdog 节拍从 YAML 读，也是启动时生效。
- **secret.key 是密码加密密钥**，丢失则已存密码无法解密；备份 = 拷整个 data/ 目录。
- 密码字段**只写不读**：编辑表单留空表示不修改。

### 4.5 错误处理体系

- **服务层返回约定**：公开编排函数返回 `{"ok": bool, "error"/"msg": ...}` dict，不抛异常；
  错误落 Job.status/JobEvent。orchestrator 头部 docstring 写明了这个约定和事务约定
  （每个编排函数内部自行 commit，中间态对进度页可见是刻意的）。
- **统一脱敏**：所有要展示/落库的外部异常必须过 `crypto.sanitize_error`
  （驱动异常会带连接串密码）。这是全库约定，新代码不得用裸 `str(e)` 落库或透出。
- **goto() 统一跳转**（templating.py）：flash 走 query 参数、htmx 走 HX-Redirect、
  超 300 字截断（中文 URL 编码 9 字节/字，防 URL 撑爆）。68 个端点没有一个自己拼
  RedirectResponse。
- **错误消息给足定位信息**：SeaTunnel errorMsg 保留头 300+尾 1700（根因在 Caused by
  链末尾）、日志截尾无 ERROR 时自动把全文 ERROR 块提到最前、DDL 失败附 SQL 上下文、
  schema change 超时附 Doris 排查指引。新功能报错也请按这个标准写。

### 4.6 降级策略（外部依赖挂了时的统一回答）

- monitor 全模块：失败不抛异常，返回 partial + error 字段。
- health：连接测试失败不阻塞保存。
- proto 裁剪：任何异常返回原文——可用性优先于精简。
- 元数据发现失败：落 metadata_status="error"，页面提示，不影响数据源其他功能。

### 4.7 留档与清理

| 数据 | 策略 |
|---|---|
| JobVersion（conf 快照） | 每次渲染留一版，**全量留档不清理**（更新失败回滚靠它） |
| JobEvent（事件时间线） | 状态变化/DDL/迁移/告警都留，**全量留档不清理** |
| MetricSample（监控指标） | 保留 14 天（`watchdog.metrics_retention_days` 可调），每日自动 prune |
| BatchTask/BatchItem | 全量留档，进度页展示靠它 |

内部工具规模下 versions/events 增长可忽略；需要瘦身时直接删表即可（README 有写明）。

## 5. 关键流程

### 5.1 作业生命周期

创建向导（4 步：源 → 映射 → 目标 → 高级选项）→ DRAFT（创建时预渲染 conf 留档，
失败不阻断）→ submit（CAS 抢状态 → 防双写 → 渲染 → ensure_table 预检 → 提交
SeaTunnel）→ RUNNING ⇄ stop（带 savepoint）/ update_and_restart → FAILED/ERROR
由 watchdog 轮询收敛 → delete（取消远端 + 删记录，集群不可达时拒绝删除防孤儿作业双写）。

### 5.2 更新并重启（update_and_restart，orchestrator 最长函数，~150 行线性 runbook）

预检（CAS → 远端在跑核实）→ 停旧作业（savepoint）→ 等终态（等不到就中止并保持运行，
防 SeaTunnel 重复提交 no-op 假成功）→ DDL 演进（ensure_table dry-run 预检）→ 渲染新
conf → 重提交 → 失败回滚到上一版本（JobVersion）。**它有 170+ 行端到端测试罩着
（test_orch.py），刻意不拆小函数**——改动它的行为时再顺手拆，现在拆是纯冒险。

### 5.3 数据迁移重建（orchestrator.migrate_recreate）

路由只留表单解析；编排在 services：compat 检查 → 迁移决策校验（列冲突取舍，决策有误
返回 exprs_errors 由路由重渲染选择页）→ 远端在跑核实 → stop(savepoint) → 等终态 →
RENAME 原表为 tmp_ → 建新表 → INSERT SELECT（含 epoch 毫秒自适应转换）→ 行数核对
→ 删 tmp → 按原状态恢复作业。**迁移失败自动回滚表名（数据不丢）并尽量恢复作业**；
行数不一致时保留 tmp 表待人工核对。端到端测试在 test_recreate.py（成功/回滚/远端残留
三路径）。

### 5.4 批量

- **批量创建**（pages/batch.py）：共享配置一次校验（`_batch_validate_shared`），逐对象
  生成映射（mapping_gen）→ 建 Job → 预渲染，结果页逐对象展示成败。
- **批量操作**（batch_ops.py）：启停/删除/改配置/更新重启，以 BatchTask/BatchItem 落库
  驱动进度页；外层兜底防任务卡死；重启进程时 main 收敛中断任务。

### 5.5 映射生成与渲染管线

proto 包（proto_center 抓取/解析/版本 diff）→ flattened_schema_fields →
`field_mapping.build_mapping`（纯函数：源类型 → ST 类型 → Doris 类型，含嵌套/VARIANT
降级）→ `apply_model_ttl`（模型/TTL 域规则）→ `render.render_and_save`（conf 渲染 +
加密落库 + 版本快照）。每一步都可单独测试（test_smoke.py 的主力覆盖）。

## 6. 开发规范

### 6.1 新代码放哪

| 是什么 | 放哪 |
|---|---|
| 页面端点/表单校验 | `api/pages/<领域>.py`；跨 2 个以上模块的表单辅助才进 `pages/common.py` |
| htmx 联动片段/JSON | `api/fragments.py` |
| 编排（多步骤、有副作用、要留事件） | `services/orchestrator.py` 或 `batch_ops.py` |
| 纯业务逻辑/纯函数 | 对应 services 模块；纯函数优先（不碰 DB/连接，喂 dict 就能测） |
| 基础设施（无业务语义） | `core/` |

### 6.2 命名与可见性

- 下划线前缀 = 模块私有。**跨模块引用私有成员就是该转正的信号**：改名去下划线，
  一并更新所有调用方（ precedent：`connect`/`SYSTEM_DBS`/`admin_kwargs`/`build_uri`/
  `NAME_RE`/`form_dict` 都是这样转正的）。
- 服务层公开函数返回 `{"ok": ...}` dict 的，docstring 说明键；路由层函数 docstring 说明
  页面行为与边界情况。
- 不为"对称好看"提取函数：行为/文案各有差异的相似代码，宁留两份（评审确认的共识：
  过度提取比重复更难读）。真正一字不差、或只差一个参数的重复才收敛。

### 6.3 注释

- 写**为什么**，不写"做什么"的复读。排障历史、踩坑结论、外部系统的怪癖（如
  `errCode 1105`、pymongo 的 bson.Int64 陷阱）直接固化在代码旁。
- 模块头部 docstring 写约定（orchestrator 的返回/事务约定、seatunnel_client 的通道
  约定、pages/__init__ 的路由顺序坑）。**下一个开发者必踩的坑，写在最显眼处。**
- 长函数允许存在，前提是线性可读 + 每段有节注释 + 测试罩着（update_and_restart 是标杆）。

### 6.4 错误处理

- 外部异常落库/透出前必须 `sanitize_error`；服务层不抛异常给路由，返回 dict。
- 失败要诚实：结果不确定就说不确定，不伪造成功也不伪造回滚。
- 用户可操作的错误给指引（如 tmp 表残留、schema change 超时都附排查/处理路径）。

### 6.5 模板与前端

- 交互用 htmx 属性，不写框架；内联 JS 保持 20~50 行小块（显隐联动/图表/计数）。
- 渲染 conf 一律 `hq/urlq` 双层转义；表单 Doris 类型/默认值走白名单正则
  （DORIS_TYPE_RE/DEFAULT_RE，防 DDL 注入）。
- 并行数组表单（字段映射 14 列）必须在 parse_mapping_form 做长度对齐校验。

### 6.6 测试

- **conftest 只放 fixture**（module 级 fresh_db/db/client，VISION_DATA_DIR 隔离数据目录
  ——必须先于 app 导入设置，conftest 注释有说明）；断言辅助 `check(name, cond, extra)`
  在 `tests/helpers.py`。
- 风格：纯函数喂 dict 断言输出；外部服务用**真 HTTP mock server**（MockSeaTunnel 模拟
  2.3.13 真实响应结构，含"metrics 值全是字符串"这种坑）；Doris 用 FakeConn 记录执行
  SQL 断言。
- 共享 mock 状态（ST dict）的用例，结束时恢复计数，别污染后续用例。
- 新增编排功能 = 新增同级端到端测试（migrate_recreate 的三路径是模板）。

### 6.7 提交与依赖

- 提交信息：`type: 中文描述`，type ∈ feat/fix/refactor/test/build/docs/chore；
  一个提交一个主题，refactor 提交不动行为。
- 依赖全部加版本上限；运行依赖 requirements.txt、开发依赖 requirements-dev.txt 分离。
- 敏感物永不入库：secret.key、data/、代理配置、私钥（.gitignore 已覆盖，提交前自查）。

## 7. 新源类型接入清单

加一种源类型（如 MySQL 源 / ClickHouse sink）要触达 11 个点位
（与 `metadata/base.py` 头部 docstring 同步维护）：

1. `models.DS_TYPES`；2. datasource 表单与 `_DS_REQUIRED`；3. `health._TESTERS`；
4. `metadata/_DISCOVERERS` + 新建 `<type>_d.py`；5. `render._TEMPLATES`；
6. `field_mapping.build_mapping`；7. `metadata/base.py` 的 source_* 导航函数；
8. `templating._ds_addr`；9. 表单模板类型显隐；10. `render.render_conf` 的
mongo_cdc 式特判；11. 批量向导模板（job_batch_form.html）。

字典分派 + if-elif 链对"就这四类"是恰到好处，**不要提前抽象成插件注册机制**。

## 8. 已知限制与刻意不做的事

**已知限制（接受，不计划修）**：

- 引擎/作业日志整文读入内存再截尾（SeaTunnel 主日志可达上百 MB；内网+日志滚动可接受，
  且"全文找 ERROR 提前"功能本身依赖全文）。
- 批量改配置会把 kafka 专属键 merge 进所有类型作业的 options（垃圾键无害，渲染按模板取键）。
- watchdog 五个轮询函数没有直接测试（逻辑简单、失败只记日志，靠集成路径间接覆盖）。

**刻意不做（评审共识，别再提）**：

- 不拆 `update_and_restart`（150 行线性 runbook + 全量测试，改动行为时再顺手拆）；
  不拆 `doris_ddl.py`（805 行但纯函数测试极好，膨胀到 ~1200 行再考虑三分）。
- 不引入插件注册框架、依赖注入容器；不把 SQLite 换 Postgres；不拆服务进程、
  不加消息队列/worker 层。对当前规模全是过度设计——**"简单直观"是这个库最大的优点**。
- 评估文档不入库则已，入库必标注对应 commit（本目录的评审存档是范例）。
