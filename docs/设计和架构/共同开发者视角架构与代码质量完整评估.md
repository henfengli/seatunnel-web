# SeaTunnel 作业管理平台 —— 共同开发者视角架构与代码质量完整评估

> 评估对象：`github.com/henfengli/seatunnel-web` master @ `2c995f3`（含 refactor/architecture-cleanup 两轮合并）
> 评估方式：全量通读源码（app/ 约 6.1k 行 Python + 3.1k 行模板）+ 静态交叉分析 + 实跑测试套件（35 passed）
> 视角：共同开发者。不看安全合规、不看生产规格，只看一件事——**这个库好不好懂、好不好改、好不好继续开发**。

---

## 0. 总体结论

**这是一份质量明显高于平均水准的代码库，可以继续放心往下开发。**

最直观的证据不是某个亮点，而是**一致性**：全库统一的 `{"ok": bool, ...}` 返回约定、统一的 `decrypt_conn/mask_conn` 入口、统一的 `goto()` flash 跳转、统一的 `run_in_threadpool` 包裹真实连接探测、几乎每个"为什么"都有注释说明（CAS 为什么、重试为什么不跨 master、为什么截断 flash、为什么是 VARCHAR(512)）。读起来能明显感到写代码的人在给下一个读代码的人留路标。

实测验证：35 个 pytest 全部通过，pyflakes 全库仅 1 个 intentional 的 `noqa` 导入，零未使用导入，路由层没有和框架打架的痕迹。

但重构两轮之后留下了一些**该收的尾巴**，以及两个结构性问题值得在下一轮迭代处理：

1. **三条死链**：一个死函数（`diff_columns`）、一条死配置链（`doris_naming.default_db`）、一个端到端死功能（环境级 `proto_site`），都是重构后没人消费的残留，正在误导读者。
2. **最复杂的编排放错了层**：数据迁移重建（停作业→RENAME→迁移→恢复，103 行）写在路由函数里，而比它简单的 submit/stop/update 都在 `orchestrator`。
3. **Doris 连接构建三胞胎**：`pymysql.connect` 参数块在三处各写一遍，已经开始漂移（超时参数三处都不一样）。

下面分层细说。

## 1. 架构评估

### 1.1 分层与依赖方向

```
api/pages/* + api/fragments.py   页面路由（68 个端点，表单校验、跳转、片段渲染）
        │  ↓ 调用
services/                        编排、DDL、渲染、元数据、监控、看护（纯业务，不碰 Request）
        │  ↓ 调用
core/                            config / db / crypto / fmt（无向上依赖）
models.py                        SQLAlchemy 模型（被各层引用）
templating.py                    Jinja2 引擎 + Web 层公共工具
```

**主干依赖方向是干净的**：api → services → core，没有反向。`services/seatunnel_client.py` 头部那句"平台与 SeaTunnel 集群的唯一 HTTP 通道……不要各自再发 HTTP"确实被执行了——全库 grep 不到第二个向 SeaTunnel 发请求的入口。`orchestrator` 头部把返回约定和事务约定写成 module docstring，调用方不需要猜。

**四个例外，按重要度排序**：

| # | 问题 | 位置 | 评价 |
|---|---|---|---|
| A1 | **迁移重建编排在路由层** | `api/pages/job.py:433 job_recreate_table`（103 行） | 全库最复杂的一段编排（stop(savepoint) → wait_terminal → migrate → 失败回滚 → resume），直接写在 POST 路由里，手工包了 8 次 `run_in_threadpool`。比它简单的 submit/stop/update_and_restart 都在 `orchestrator`。**这是分层上最刺眼的不一致**——读者会形成"编排都在 services"的预期，然后在这里破功。 |
| A2 | 域规则混在 Web 层 | `api/pages/common.py:139 apply_model_ttl`（64 行） | "TTL 列必须是 DATE/DATETIME/BIGINT/STRING、BIGINT 要改类型为 DATETIMEV2(3) 并打 ms_epoch 标记、AGGREGATE 模型不许 nested 列"——这些是 Doris 域规则，不是表单解析。它现在和 `parse_mapping_form`（纯 Web 关注点）住在同一个文件里。哪天要加 API/CLI 入口，这段逻辑得先搬家。 |
| A3 | orchestrator 兼任 options 访问器 | `orchestrator.job_ttl/job_model/job_buckets` | 三个纯函数只读 `job.options`，和"编排"没有任何关系，但 job.py 的路由为了读配置不得不 import 编排模块。应该挪到 models.py（做成 Job 的方法/property）或独立的 `job_options.py`。 |
| A4 | templating 依赖 services | `templating.py` import `envs` | 为了 base.html 顶栏的环境名列表，模板引擎这个"准基础设施"反向依赖了服务层。注释里解释了动机（避免 services → templating 反向依赖），方向选对了，但更干净的做法是把 `all_env_names` 的提供者注入（在 main.py 里注册 global），而不是 templating 自己 import。小问题。 |

### 1.2 技术选型与复杂度匹配

FastAPI + Jinja2 SSR + htmx + SQLite(WAL) + APScheduler 单进程，对一个"几十条作业、几个用户、内网单机"的平台是**恰到好处的复杂度**。没有引入任何用不上的东西：没有消息队列、没有 worker 层、没有前端构建链（static/ 就 htmx + chart.js + 231 行 CSS）。模板里的内联 JS 全部是 20~50 行的小块（显隐联动、图表渲染），没有失控。

两个选型决策特别值得点名：

- **`JsonDict` 列类型**（core/db.py）：把"TEXT 列存 JSON"的样板收进 TypeDecorator，列名保持 `*_json` 兼容旧库。这一刀砍掉了 models 里成片的 `*_json + property` 样板，是重构价值的典型体现。
- **`goto()` 统一跳转**（templating.py）：flash 走 query 参数、htmx 走 HX-Redirect、超长截断防 URL 撑爆——一个函数把 SSR + htmx 混编的跳转问题收敛了，68 个端点没有一个自己拼 RedirectResponse。

### 1.3 状态机与并发设计

作业状态机（DRAFT/RUNNING/STOPPED/FAILED/UPDATING/ERROR）设计得很扎实，这是全库技术含量最高的部分：

- **CAS 防并发**：submit 和 update_and_restart 都用 `UPDATE ... WHERE status IN (...)`, 原子抢状态，批量+手动+双击并发提交出双作业的场景被堵死，CAS 失败还会 expire 后读真实状态再报错。
- **状态白名单** `SUBMITTABLE_STATES`：防线在服务层而不依赖调用方。
- **防双写**：`_find_running_conflict` 查同 env+同数据源+同源对象的 RUNNING 作业，从业务根上防"两个作业全量消费同一 topic 写双份"。
- **歧义处理诚实**：update 提交失败时不伪造回滚——先查 SeaTunnel 侧实际状态，"结果不确定"就明说不确定、请人工核对，而不是假装回滚成功。这是写过真系统的人才有的意识。
- **watchdog 与编排的边界**：UPDATING 不参与状态轮询（编排线程自己管），refresh_status 不动 UPDATING——避免了轮询和编排竞争出假迁移。

## 2. 代码质量评估（做得好的地方）

1. **注释质量是全库最大的资产**。不是"做什么"的复读注释，而是"为什么"：`retry=False 只试第一个 master——非幂等请求跨 master 重试可能产生重复作业`、`errCode 1105: String Type should not be used in key column`、`pymongo 对 int64 返回 bson.Int64（int 子类，必须先于 int 判断）……此前的 abs()>=2^31 猜测会误判（OrderEvent exchange_time 实际案例）`。这类注释直接把排障历史固化进了代码。
2. **纯函数与副作用分离**。`doris_ddl.compat_decision`、`build_migration_plan`、`build_select_exprs`、`field_mapping.build_mapping` 都是不碰连接的纯函数，测试直接喂 dict 就能跑——test_recreate.py 近 600 行测试就是建立在这个设计上的。
3. **降级策略一致**。monitor 全模块"失败不抛异常，返回 partial + error 字段"；health "失败不阻塞保存"；proto 裁剪"任何异常返回原文——可用性优先于精简"。整套系统对"外部依赖挂了"这件事的回答是统一且可预期的。
4. **防御性细节成体系**：错误消息统一 `sanitize_error` 脱敏（驱动异常会带连接串密码）、conf 渲染 `hq/urlq` 双层转义、表单 Doris 类型/默认值白名单（`DORIS_TYPE_RE/DEFAULT_RE`）、`parse_mapping_form` 14 个并行数组长度校验。
5. **测试是真的在测业务**。MockSeaTunnel 用真 HTTP server 模拟 2.3.13 的真实响应结构（metrics 值全是字符串这种坑都模拟了）；conftest 用 `VISION_DATA_DIR` 隔离数据目录，注释说明了为什么必须先于 app 导入设置。
6. **工程卫生**：依赖全部加版本上限、requirements-dev 分离、.gitignore 合理、git 提交信息规范且按 refactor/fix/test/build 分类。

## 4. 优化方向（按性价比排序）

按"花的功夫 vs 后续开发收益"排序，供下一轮迭代参考：

1. **清死链（半天）**：D1~D4。删 `diff_columns`、摘掉或接上 `default_db` 与 `proto_site`、删空文档。纯减法是风险最低、可读性收益最高的动作。
2. **私有函数转正 + Doris 连接收敛（半天）**：P1~P3 + R1 一起做——`_connect` 改名 `connect` 并从三处收拢，`admin_kwargs`/`_build_uri` 去下划线。
3. **迁移重建编排下沉到 services（一天）**：A1。把 `job_recreate_table` 的编排段抽成 `orchestrator.migrate_recreate(db, job, mode, decisions)`，路由只留表单解析和 goto。顺带解决 M1 的一部分——它是和 update_and_restart 同级的编排，应该接受同级的测试（test_recreate 已有半截可直接扩）。
4. **options 访问器归位（一小时）**：A3，`job_ttl/job_model/job_buckets` 挪到 models.Job 上，api 层不再为读配置 import orchestrator。
5. **小重复收敛（半天）**：R2~R7 各抽一个小函数。
6. **JsonDict 变更跟踪（十分钟）**：M2，加 `MutableDict.as_mutable` 或补纪律注释。
7. **新源类型接入清单注释（半小时）**：3.4 节，一行注释清单即可，不做提前抽象。

不建议做的：引入插件注册框架、把 SQLite 换 Postgres、给路由加依赖注入容器、拆分服务进程——对当前规模全是过度设计，现有架构的"简单直观"正是它最大的优点。

## 6. 一句话总结

**架构合理、约定统一、注释诚实、测试务实，是一份可以放心接手的库**；当前最值得做的不是加功能，而是花一天时间把重构残留的三条死链清掉、把迁移重建编排挪回 services 层——那之后，这份代码在"简洁直观、易懂、好维护"三个维度上就没有明显短板了。
