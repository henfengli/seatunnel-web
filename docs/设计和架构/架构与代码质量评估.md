# SeaTunnel 作业管理平台 —— 架构与代码质量评估

> 版本：当前主干（含批量操作/数据迁移重建/在线演进）。统计口径：`wc -l` 实测。
> 本文档目的：讲清楚系统怎么构成的、为什么这么做，以及——诚实地说——代码质量到底怎么样。

---

## 1. 项目定位与技术选型

内网环境的轻量级 SeaTunnel 作业管理平台：统一管理 Kafka(protobuf) / MongoDB / PostgreSQL / Doris → Doris 的同步作业。使用方是量化数据团队，部署目标是**一台内网 Linux 机器 + conda 环境**，无外网、无 Node 构建链、无容器。

| 选择 | 方案 | 理由（也是约束） |
|---|---|---|
| Web 框架 | FastAPI + Jinja2 服务端渲染 | 内网无外网，前后端分离的构建链（npm/CDN）不可用 |
| 前端交互 | htmx + 少量原生 JS + Chart.js（全部本地化） | 够用且不引入构建步骤；页面即模板，改动即生效 |
| 数据库 | SQLite（WAL） | 单机部署、零运维；备份=拷目录；写入量小（监控样本每分钟几十条） |
| 任务调度 | APScheduler（BackgroundScheduler） | 状态轮询/指标采集/元数据刷新/proto 轮询，都在进程内 |
| 与 SeaTunnel | 仅 REST API | 平台重启/升级不影响在跑作业 |
| 与 Doris | MySQL 协议（pymysql） | information_schema + SHOW CREATE TABLE + DDL 全部走 9030 |

**这些选型直接决定了架构形状**：单进程、服务端渲染、同步编排、无消息队列、无 worker 层。对于"几十条同步作业 + 几个用户"的规模，这是合适的复杂度；任何更重的方案都是过度设计。

## 2. 总体架构

```
浏览器 ──► FastAPI（单进程 uvicorn）
           ├─ api/pages.py        页面路由（表单提交、编排入口、批量入口）
           ├─ api/json_api.py     htmx 片段/JSON 辅助路由
           ├─ services/
           │   ├─ orchestrator.py   提交/停止/更新编排（状态机 + CAS + 回滚）
           │   ├─ doris_ddl.py      Doris 建表/在线演进/兼容判定/数据迁移
           │   ├─ render.py         HOCON conf 渲染（Jinja2，独立模板目录）
           │   ├─ field_mapping.py  源类型 → SeaTunnel → Doris 类型映射
           │   ├─ proto_center.py   proto 拉取/解析/diff/裁剪
           │   ├─ metadata/         各数据源元数据发现（topics/库表字段）
           │   ├─ monitor.py        监控只读查询（速率/lag/日志/集群概览）
           │   ├─ batch_ops.py      批量任务执行（后台线程）
           │   ├─ watchdog.py       定时看护（状态/指标/元数据/proto/告警/清理）
           │   └─ envs.py/health.py 环境配置与连接测试
           ├─ models.py           SQLAlchemy 模型（7 张表）
           └─ core/               配置/SQLite/加密(Fernet)
                │
                ├─► SeaTunnel 集群（REST: submit/stop/job-info/logs/checkpoints）
                ├─► Doris（MySQL 协议：DDL/信息查询）
                └─► Kafka/MongoDB/PG（元数据发现、lag、健康检查）
```

**进程模型**：一个进程里三类执行流——

1. **请求线程**：页面与表单处理，同步调用编排（提交一次作业 = 建表 + 渲染 + REST 提交，秒级）。
2. **APScheduler 后台线程**：5 个定时任务，均 `max_instances=1 + coalesce`，不堆积。
3. **批量任务 daemon 线程**：一个批量任务一个线程，串行执行逐条落库，页面 2s 轮询进度。

没有消息队列、没有分布式锁。并发安全靠三件事：SQLite WAL（读写不互斥）、**状态 CAS**（提交/更新前原子迁移状态防并发双跑）、定时任务单实例。

## 4. 核心数据流

### 4.1 作业生命周期（创建 → 提交 → 更新 → 删除）

```
向导/批量建 → DRAFT（渲染预留档）
   │
   ▼ submit（CAS: 状态→UPDATING，防并发双跑）
  ① 防重复消费检查（同 env+数据源+源对象 的 RUNNING 作业）
  ② savepoint 就绪检查（恢复场景：旧作业未终态则等，等不到拒）
  ③ ensure_table（§4.2）——需重建则拒绝并恢复状态
  ④ render_and_save（conf 渲染 + 加密留档 JobVersion）
  ⑤ /submit-job（不跨 master 重试，防歧义重复提交）
   │
   ▼ RUNNING ── watchdog 15s 轮询 job-info，FAILED 时 errorMsg 落 status_detail + 钉钉聚合告警
   │
   ▼ update_and_restart（更新并重启）
  预检(dry_run 兼容判定，需重建直接拒，作业保持运行)
   → 核实旧作业真实状态（stop 失败残留也按在跑处理）
   → stop(savepoint) → _wait_terminal（等不到终态中止，不冒险重提交）
   → ensure_table 在线演进 → 渲染留档 → savepoint 重启
   → 提交歧义检查（疑已生效如实上报，不伪造回滚）；真失败回滚上一版 conf+映射
   │
   ▼ 删除 = 取消 SeaTunnel 作业（集群不可达则拒绝）+ 级联清理（versions/events/metrics）
```

关键认知（从 SeaTunnel 源码确认并写进了代码注释）：**对仍在运行的同 jobId 重复提交，SeaTunnel 返回成功但不应用新配置**——所以"等终态"和"不盲目重试"是正确性的命门，不是洁癖。

### 4.2 Doris 表结构演进（ensure_table 三级判定）

```
check_compat（information_schema + SHOW CREATE TABLE）
  ├─ 表不存在 → CREATE（模型/key/TTL 动态分区/分桶）
  ├─ online  → ADD COLUMN / MODIFY COLUMN（官方转换矩阵保守子集；key 带 KEY、
  │            AGG value 带聚合函数、重述原 DEFAULT）/ 动态分区 ALTER（TTL 窗口）
  │            —— 执行器：SCHEMA_CHANGE 忙等待重试 + "Nothing is changed" 幂等跳过
  └─ recreate→ 不执行，返回原因清单（模型/key 不一致、未分区启用 TTL、
               收窄转换、分区列/分桶列变更），提交/更新预检直接拒绝
```

类型比对前先做 `_canon_type` 归一化（依据 Doris BE `schema_columns_scanner.cpp` 的 COLUMN_TYPE 输出规则）：`tinyint(1)→BOOLEAN`、`datetime(p)→DATETIMEV2(p)`、`text/string→STRING`、`decimalv3→DECIMAL`、整型显示宽度剥除。这是消灭"平台建的表和平台读回的表互相不认识"的根。

### 4.3 数据迁移重建（保留数据的重建）

```
RUNNING? → stop(savepoint)
→ 检查 tmp 残留 → RENAME 原表为 tmp_ → 按新配置建新表
→ TTL 表：关动态分区开关 → 按 tmp 实际数据补建历史分区（date_trunc；ms_epoch 列先 from_millisecond）→ 开开关
→ INSERT INTO 新表 SELECT（逐列方案：same/安全 CAST/风险 CAST 用户决策/新列填充常量/epoch 列 from_millisecond）
→ 行数核对（UNIQUE/AGG 允许变少）→ 删 tmp（不一致则保留待人工）
→ 失败回滚：删半成品新表、tmp 改回原名；RUNNING 起的作业按 savepoint 恢复
```

### 4.4 监控采集

`watchdog` 每 60s 对每个 RUNNING 作业采 `/job-info` 的累计计数（值全是字符串，防御性展开），落 `metric_samples`（保留 14 天每日清理）。速率图/写入统计全部用**相邻样本差分**——不用引擎自报 QPS（重启清零语义差）。kafka lag 用 `consumer.committed()` vs `end_offsets()`（offset 由 SeaTunnel 在 checkpoint 时提交 broker）。

## 5. 数据模型（7 张表 + 2 张批量表）

- `environments`：环境 = masters + Doris 连接 + proto 站点；密码 Fernet 加密；`environments.yaml` 仅首启种子
- `datasources`：连接信息（密码加密）+ 元数据缓存 + 健康状态
- `proto_packages`：原文/解析产物/上一版/diff/轮询配置
- `jobs`：作业定义（mapping/options JSON、状态、SeaTunnel jobId）；`seatunnel_conf` 加密落库
- `job_versions`：每次渲染的 conf（加密）+ 映射 + DDL 快照
- `job_events`：操作事件流（平台侧排障的第一现场，日志面板上半部分）
- `metric_samples`：分钟级累计计数（14 天保留）
- `batch_tasks` / `batch_items`：批量任务与逐条结果（启动时收敛中断任务）

密码相关规则：表单只写不读、落库必加密、展示必掩码、conf 渲染产物也加密、`sanitize_error` 给异常消息脱敏。

## 6. 代码质量评估（诚实版）

### 6.1 做得好的地方

- **复杂度与规模匹配**。没有为了"显得专业"引入用不上的东西（无 MQ、无 ORM 滥用、无前端框架）。每台机器一份 `data/` 目录就是全部状态。
- **分层清晰、纯函数可测**。`compat_decision`/`build_mapping`/`subset_proto`/`build_select_exprs` 都是纯函数；五套测试（约 160+ 断言）覆盖渲染管线、DDL 生成、兼容判定、迁移 SQL 序列、编排 mock 全流程、30 个路由渲染。
- **防御性外部交互**。所有外部调用有超时+降级；DDL 幂等（重放不炸）；错误带 SQL 上下文；Doris 异步 schema change 有等待重试。
- **审计传统**。类型显示名、DDL 语法、REST 语义都对照过 Doris/SeaTunnel 源码或官方文档，注释里写明出处——不是"大概能跑"。
- **排障友好**。平台事件流 + SeaTunnel 日志双视图、批量逐条结果、conf/DDL 全量留档。

### 6.2 真实存在的问题（技术债，按痛感排序）

1. **`pages.py` 1793 行，明显过大**。路由+表单解析+校验+部分编排胶水全在一个文件。每次加功能都往这里塞，函数平均长度在涨。**这是全项目最像"屎山前兆"的地方**。合理拆分：`routes_datasource.py` / `routes_proto.py` / `routes_jobs.py` / `routes_batch.py` / `form_parse.py`。目前没拆的原因是路由间共享小工具多，拆分需要一次纯粹的搬运重构（机械、低风险、但没业务收益所以一直让位）。

2. **表单协议靠 hidden 字段对齐，脆弱**。字段映射编辑 = 每行 14 个 `map_*` hidden 输入，服务端按 getlist 等长解析。加一个新 mapping 键（如这次的 `ms_epoch`）要同时改两个模板 + 解析 + 测试，漏一处就是"映射不完整"。这是服务端渲染无组件化的固有代价，可接受但要意识到它是改动密集区。

3. **类型知识分散在三层**。`_canon_type`（读回归一化）/`MONGO_TYPE_MAP` 等（源→ST→Doris 映射）/`ST_SCALAR_TO_DORIS`/`_effective_type`/`_column_def` 五处都"懂类型"。每次类型相关 bug（BOOLEAN、DATETIMEV2、TEXT、enum…）都要在多处同步修。理想形态是一份"类型注册表"统辖，现状是注释互相引用。这是历史演进而非设计，**是目前最需要警惕的熵增点**。

4. **模板里的原生 JS 是零散的**。每个页面一小坨 `<script>`（显隐切换、过滤、计数），无 lint 无测试，靠 pages_test 的"渲染不 500"兜底。交互还简单，可控；再复杂就该收编。

5. **测试与代码同人编写的共同盲区**（已被代理审计实证过一次：删除守卫的 `_job_info` 从不抛异常，测试却以为它会）。缓解：引入了多代理交叉审计；根本缓解还是要补"真实 Doris/SeaTunnel 冒烟"（内网环境做得到，值得加一条手动跑的 e2e 清单）。

6. **单进程天花板**。所有编排同步执行，批量 200 个作业的串行跑要几分钟（设计如此，进度页轮询）；uvicorn 单 worker 下慢请求会拖其他页面响应。当前规模无感，作业量×10 才需要动。

7. **小不一致**：`render.py` 里 `from . import proto_center` 在函数内 import（防循环）与文件顶部混用；`orchestrator` 的私有函数（`_get`/`_post`/`_wait_terminal`）被 pages/batch_ops 跨模块直接调用——约定俗成但名义上是"私有"。

### 6.3 结论：是不是屎山

**不是屎山，但处在"需要开始还利息"的阶段。**

- 地基（分层、纯函数、测试、审计注释）是好的，这也被证明过：类型系统三次大返工都控制在 `doris_ddl.py` + 测试内，没有扩散。
- 风险集中在三处：`pages.py` 的体量、hidden 表单协议的改动成本、类型知识的三处分散。它们现在都不疼，但每一条都是"再加三个功能就会疼"的类型。
- 建议的还债顺序（都不紧急）：① 拆 `pages.py`（纯搬运）；② 类型知识收拢成一个模块；③ 补一条内网真实 e2e 冒烟清单。做完任意一件之前，新功能的边际成本都在可接受范围。

## 7. 关键设计决策速查（为什么是这样，而非拍脑袋）

| 决策 | 原因 |
|---|---|
| submit 不跨 master 重试 | 非幂等：超时歧义会重复提交出双作业（SeaTunnel 重复提交 no-op 成功） |
| 更新前 dry_run 兼容预检 | 需重建的冲突在停作业前拒绝，作业保持运行 |
| savepoint 等终态，等不到中止 | 重复提交假成功是正确性命门 |
| DDL 幂等 + 忙等待 | Doris schema change 异步；重放/竞态是常态 |
| 类型归一化 `_canon_type` | MySQL 协议显示名 ≠ Doris 规范名（BE scanner 源码为准） |
| Mongo 一律走 BSON 类型+validator | 按值猜类型已被证明不可靠（OrderEvent 案例） |
| 速率用样本差分 | 引擎 QPS 在重启/计数清零时语义差 |
| conf 加密落库 | 渲染产物含明文密码，DB 文件即机密 |
| 批量串行 + 逐条落库 | 维护窗口操作，可观测、可断点收敛，不压 master |
| SQLite WAL + 状态 CAS | 单进程下的并发正确性最低成本组合 |
